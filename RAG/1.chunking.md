# RAG From Scratch

## 1. Embeddings + Mini Semantic Search — Recap
Already built this in Mini-Project 0 (`sentences.py`, `embedd.py`, `cosine_similarty.py`, `searching.py`): embed text → vectors → store in numpy array → rank by cosine similarity. No vector DB needed at small scale.

**Interview answer:** "A minimal semantic search system needs an embedding model, a numpy array to store vectors, and a cosine similarity function to rank against a query. A vector database only becomes necessary once brute-force comparison stops being fast enough."

## 2. Chunking — Why It Exists
Can't embed a whole document as one vector — averages away detail. Split into smaller **chunks** first, each gets its own vector.

- **Fixed-size**: split every N chars/tokens. Simple, fast, can cut mid-sentence.
- **Recursive** (common default, e.g. LangChain's RecursiveCharacterTextSplitter): tries paragraph → sentence → word boundaries first, hard-cuts only if still too big. More coherent chunks.
- **Semantic chunking**: split where topic actually shifts (detected via embedding similarity between consecutive sentences), not by size. More sophisticated, more expensive.
- **Chunk overlap**: consecutive chunks share a bit of text (e.g. last 50 chars of chunk 1 = first 50 of chunk 2) — prevents losing a sentence that falls right on a cut line.

**Simple words:** chunking = cutting long docs into smaller pieces before embedding, since one giant vector per document loses detail. Fixed-size = simple but can cut mid-sentence. Recursive = respects natural breaks. Semantic = splits by topic change. Overlap = prevents losing content right at a cut line.

**Interview answer:** "Chunking splits documents before embedding since embedding an entire document loses fine-grained detail. Fixed-size chunking is simple but can cut mid-sentence; recursive chunking splits on natural boundaries as a better default; semantic chunking splits based on topic shifts via embedding similarity. Chunk overlap prevents losing context at boundaries by duplicating a small amount of text between consecutive chunks."

## 3. The Full RAG Pipeline By Hand
Two phases: **retrieval** (stages 1-5) + **generation** (stages 6-7) = "Retrieval-Augmented Generation."

1. **Load** — read raw documents (.txt/.md/PDF) as plain text
2. **Chunk** — split into smaller pieces (recursive = sensible default)
3. **Embed** — convert each chunk to a vector
4. **Store** — keep chunk text + embeddings together (numpy array + parallel list at small scale — same as Mini-Project 0)
5. **Retrieve top-k** — embed the user's question, cosine similarity search for k most similar chunks
6. **Stuff into prompt** — insert top-k chunks as context, followed by the question:
```
Context:
[chunk 1] [chunk 2] [chunk 3]
Question: {user question}
Answer using ONLY the context above.
```
7. **Answer with citations** — model references which chunk(s) it used, so the answer is verifiable against real sources.

**Simple words:** RAG = load docs, cut into chunks, vectorize each chunk, keep vectors + text together, find the most relevant chunks for a question via similarity search, paste those into the prompt, ask the model to answer using only that context (and cite where it got it).

**Interview answer:** "RAG has two phases: retrieval (load, chunk, embed, store, retrieve top-k via similarity search) and generation (inject retrieved chunks into the prompt as context, have the LLM answer grounded in that context, ideally with citations). Grounding in retrieved real text is what reduces hallucination compared to relying purely on the model's training knowledge."

## 4. RAG Failure Modes
RAG can fail at multiple points — diagnosing WHICH stage failed matters.

- **Bad chunking**: too large = dilutes relevance; too small = loses context (e.g. "it" with no referent).
- **Wrong k**: too few = miss the answer chunk; too many = dilute prompt, risk "lost in the middle."
- **Query-document style mismatch**: short question vs formal doc paragraph can score lower similarity than expected, pushing the right chunk out of top-k.
- **Retrieval vs generation failure (key diagnostic split)**:
  - Retrieval failure = right chunk never found at all (fix: better chunking/embeddings/hybrid search/re-ranking)
  - Generation failure = right chunk WAS retrieved, model still answered wrong (fix: better prompt/stronger model)

**How to diagnose:** manually check what chunks were actually retrieved for a failing query. Not there → retrieval failure. There but ignored/misused → generation failure.

**Simple words:** RAG breaks at either end — system never finds the right info (retrieval failure), or finds it but the model still messes up (generation failure). Always check what was actually retrieved before blaming the prompt or model.

**Interview answer:** "RAG failures split into retrieval failures (correct chunk never found — bad chunking, wrong k, query-document mismatch) and generation failures (correct chunk retrieved but model still answered poorly). Diagnose by inspecting actually-retrieved chunks for a failing query — each failure type needs a completely different fix."

## 5. RAG vs Long-Context vs Fine-Tuning
- **RAG**: knowledge changes often, need citations/trust, knowledge base too big for any context window, don't want to retrain on data changes.
- **Long-context**: data small enough to fit, need holistic reasoning across a whole doc, simplicity over efficiency. Still subject to "lost in the middle."
- **Fine-tuning**: change style/tone/output format, lower latency/cost at scale, domain-specific language patterns. NOT for new facts/knowledge — weights are frozen at training time, doesn't update live like RAG does.

**Classic interview scenario:** "Client wants a chatbot over internal docs — which approach?" → **RAG** (large, frequently-updated, needs citations — textbook use case).

**Simple words:** RAG = look things up on demand (good for changing facts + citations). Long-context = paste everything into the prompt (good for small docs / whole-document reasoning). Fine-tuning = permanently teach style/behavior, NOT a good way to teach new facts.

**Interview answer:** "RAG suits large, frequently-updated, citation-needing knowledge. Long-context suits small enough data needing holistic reasoning, still subject to lost-in-the-middle. Fine-tuning suits consistent style/tone/domain patterns, not factual currency — since that requires retraining, unlike RAG's live knowledge base."
